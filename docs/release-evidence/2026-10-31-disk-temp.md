# Disk-backed development scratch

The maintainer reported a host application crash and requested that project work stop using RAM-backed system `/tmp`. Live inspection confirmed `/tmp` is tmpfs and the checkout is on Btrfs, with approximately 158 GiB free at inspection. New [local storage instructions](../LOCAL_TEMP_STORAGE.md), `AGENTS.md` and `CI/with_disk_tmp.sh` direct local build, test and extraction commands to the checkout's ignored private `tmp/`. The shared Python helper rejects RAM-backed filesystems on Linux, verifies private ownership/permissions, exports the standard temporary-directory variables and resets Python's cached selection where invoked directly. Main Linux build entrypoints and Boost/package smoke tools configure this automatically; arbitrary commands use the launcher or exported variables.

The three acceptance container wrappers now bind private disk scratch at container `/tmp`, including applications that use that literal path for X11 sockets and locks. Scratch survives detached runs and remains alongside output for diagnostics. The overnight supervisor includes it in sampled artifact/log/headroom limits, records separate and combined sizes, rechecks final bounds and hashes the new shell helper as part of its procedure. The original eight-hour run's frozen procedure and artifacts are preserved; these changes do not retrospectively qualify or restart it. A new run would need its new procedure identity recorded. The removed 32 MiB tmpfs allocation is replaced by sampled disk accounting rather than an instantaneous filesystem quota.

The kernel journal records a global OOM at 05:05:04–05 UTC on October 31, the same interval as the native test's disconnect timeout. The killed `MainThread` was in a Chromium application scope and held 59,008,696 KiB, approximately 56.3 GiB, of anonymous RSS. Its task RSS was not tmpfs-backed shared memory. The allocation that invoked the OOM killer ran in the acceptance container's scheduling context, while the killed task belonged to a user application scope; invocation context is not evidence that the container held the memory. The test's retained cgroup peak was approximately 397.2 MiB with no container OOM event. This host-wide pressure is relevant diagnostic context, but the excerpt neither proves tmpfs was its cause nor explains that application's heap growth. Disk scratch is a concrete mitigation for temporary-file pressure, not a process-heap cap or a guarantee against another OOM.

Local validation passed 46 temporary-storage/overnight/paired-soak regression tests, three server-launcher tests and eighteen gameplay-runner tests. Tests cover environment inheritance, Python's cached temp path, private permissions, real host tmpfs rejection, wrapper paths with spaces, disk mounts, sibling scratch accounting, symlink handling, resource caps and procedure mutation detection. Shell syntax, Python parsing, four workflow YAML files and sparse helper delivery were checked. The new checks are wired into SourceChecks. Windows/macOS sparse release-tool checkouts include the imported helper, but execution on those platforms is not claimed here.

A reused, network-isolated one-shot Ubuntu container with a 128 MiB memory limit successfully wrote temporary data and created a real Xvfb X11 socket on the Btrfs-backed `/tmp` bind. A separate 512 MiB one-shot container passed all fourteen native client control-boundary cases using the new profile-local temp environment and the existing dd1fd12 client binary. These short checks require no game assets or operator gameplay and do not replace rendered gameplay or sustained operation. Both one-shot containers were removed, and only their own inactive smoke scratch was cleaned. The private native control receipt is bound by hash in the [structured storage record](2026-10-31-disk-temp.json).

Two earlier control-check attempts remain diagnostic: the sandbox blocked the local guard socket before cases ran, and a host execution then lacked the Ubuntu client's `libavcodec.so.60`. Neither is claimed as a pass; the accepted control result uses the matching cached Ubuntu runtime. No host dependency installation, game runtime change, system `/tmp` cleanup/remount, NUC update or public release occurred.
