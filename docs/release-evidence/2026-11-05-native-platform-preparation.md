# Windows and macOS stable preparation

The maintainer authorized automatic Windows/macOS verification and stable preparation after the Linux release. The selected runtime remains `a6868387dc80dcafd9b8ebad3d8c708511d9a615`, version 1.0.0, protocol 13. The published Linux package, tag, NUC deployment and existing evidence are unchanged. This checkpoint is preparation, not native-platform stable acceptance; its [structured receipt](2026-11-05-native-platform-preparation.json) preserves the actual artifacts and pending work.

The existing exact-source CI run `42025424431` passed all eleven jobs, including Windows x64 and both macOS architectures. Both macOS DMGs were downloaded for inspection: Intel SHA256 `6aaf2af3432f29382c45277ab41cb7ceb69a994363494bbb8eed54e7a82edda6` and Apple Silicon SHA256 `654f6295e608e73da2526c81a457798f22c84cb17c282de0ad0a5fe06f2006a3`. Their matching native CI startup checks remain distinct from graphical gameplay. The Windows CI install artifact contains the client but omits the dedicated server and CoreScripts; it is not a complete client/server release package. Full Windows packaging run [42057767417](https://github.com/dev-zetta/MWNet/actions/runs/42057767417) was therefore started against the exact runtime, using separately identified workflow revision `44d5660a2d32716a47b40bf93a692b9fa929b1b6`. That run is pending at this checkpoint.

Inspection found a concrete Apple Silicon provider mismatch: its actual CMake log selected OpenSSL 4.1.0 from the runner's Python toolchain, while the delivered libcrypto contains the version string `OpenSSL 3.0.16 11 Feb 2025`. This is not treated as a passing dependency identity check or proof of a particular exploit. New configure tooling explicitly selects one Homebrew OpenSSL root for headers, crypto and SSL libraries, and a new verifier checks the CMake provider, header version and actual provider/bundled runtime versions. Each library is loaded in a fresh isolated Python process so a previously loaded library cannot mask another bundled version. The new native package check must pass before those rebuilt packages can be considered. Three targeted regression tests passed, including rejection of the observed old bundle version; native execution remains pending.

Eight exact source archives totaling 132,955,582 bytes were downloaded and verified: FFmpeg 8.0.1, OpenAL Soft 1.25.0, libiconv 1.18, the pinned OpenMW OSG fork, and Qt Base/SVG for Windows 6.6.3 and macOS 6.10.3. SDK source checksums come from the preserved SDK SPDX inputs, bound to the SDK archive hashes and builder/vcpkg revisions; Qt pins come from official release checksums. The [source-input manifest](../license/third-party/native-source-inputs.json) is consumed by `CI/collect_mwnet_corresponding_sources.py`; five offline regressions passed for missing pins, unsafe URLs/names, tampered downloads/cache and preserving prior receipts. The receipt means complete delivery of these listed archives only. Full native distribution still requires actual binary-to-dependency coverage, matching build/patch material and notice/source delivery for all other bundled inputs, including runner libraries. A source list or successful download does not close that gate. Qt also carries third-party code under its own notices, as described in [Qt's licensing documentation](https://doc.qt.io/qt-6/licensing.html).

No native graphical run is claimed. The existing gameplay runner uses Linux Xvfb and POSIX process/profile handling; native Windows/macOS execution needs a matching unattended controller and private canonical game-asset access. An online Mac was visible but refused SSH on port 22, and no Windows host was visible. Native host destinations/data paths were requested while independent packaging work continues; no operator gameplay or redistribution of Morrowind data is requested. Stable support remains Linux-only until actual native graphical and complete distribution evidence pass. The maintainer-authorized AI review remains accepted; no human-review prerequisite is added.
