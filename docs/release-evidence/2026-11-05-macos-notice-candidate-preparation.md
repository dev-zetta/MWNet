# Separate Mac notice-resource candidate procedure

A separate native workflow is prepared to copy the two pinned original images' actual `MWNet.app` and `OpenMW-CS.app`, add four notice/source-reference resource files, create enclosing ad-hoc signatures and produce new ZIP/app candidates. The [procedure receipt](2026-11-05-macos-notice-candidate-preparation.json) records the unchanged DMG pins, independent controller/tool identities and notice resources. The secondary app is actually named `OpenMW-CS.app`; it is preserved under that name. No disk image is created, and the known later Intel HFS+ packaging failure remains failed.

The controller verifies each original app's deep/strict signature and exact copy inventory, including original modes and in-app symlink targets. Only explicitly added notice resources and enclosing signature metadata/main-executable signature bytes may change. For the signed main executable it compares every unsigned byte, including symbol/string tables and padding, together with section and loader identity; the signing blob, its command offsets/sizes and enclosing LINKEDIT lengths are the only normalized fields. All other original libraries, scripts and assets must retain identical bytes. Native ZIP re-extraction must preserve the complete candidate inventory, deep/strict signatures and actual client/server identity, CoreScripts initialization and clean exit using isolated server state.

Eight offline regressions passed, covering signature-only edits, code/loader/padding mutation, invalid signing bounds, notice-addition bounds, library/script/mode preservation and symlink escape rejection. YAML and all four notice-resource pins were checked. The notice book preserves upstream bytes and whitespace through explicit Git attributes. These local tests prepare the procedure; no native result or graphical/notarization/distribution acceptance is inferred. Large source material stays private, and no Linux release asset or NUC service is changed.
