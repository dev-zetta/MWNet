# Host crash diagnostics preparation

The NUC froze again while the acceptance workload was stopped and before any new host settings had been applied. The operator had disconnected HDMI and a USB hub, did not observe the precise freeze time, confirmed the machine was unresponsive and restarted it again. Boot `0282366eb8b54221a07a1ff0fd9d7b13` ends at 17:14:01 UTC; current boot `7bb206b2bbec41c09a09553222b738c7` began at 17:25:42 UTC. USB hub/receiver disconnects were logged at 17:11:03 UTC, and ordinary kernel logging continued afterward. An immediate hotplug-induced freeze is therefore not established. This recurrence was outside the acceptance workload and cannot be attributed to its resource demand from these observations.

Both affected boots' final available kernel messages concern repeated failed association attempts from the unused Intel Wi-Fi adapter. The active default route and management underlay are wired `eno1`; `wlp0s20f3` had no carrier or assigned addresses. The association messages also occurred during healthy operation, so their proximity to the cutoff is a hypothesis, not a diagnosed cause. A guarded optional mitigation soft-blocks only the unused radio, preserves its original state, verifies the wired route and persisted systemd-rfkill state, and runs only after crash logging is verified. It changes no credentials, Ethernet, Tailscale, firewall or routing settings.

The existing Ubuntu kdump capture kernel is loaded with 512 MiB reserved. Kernel/NMI watchdogs are enabled, while hard/soft-lockup panic settings and panic timeout were zero. The new [host-diagnostics implementation](../../docker/discovery/host-diagnostics/README.md) prepares detected-lockup panic capture, a private disk dump destination, shorter persistent journal sync, and a bounded fsynced host telemetry service with a private operator-readable live status. It retains the armed kernel/initrd and does not force a panic or reboot. The design follows the [kernel lockup detector controls](https://www.kernel.org/doc/html/latest/admin-guide/lockup-watchdogs.html), [Ubuntu kdump guidance](https://ubuntu.com/server/docs/how-to/software/kernel-crash-dump/) and [systemd journal configuration](https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html). A configured capture kernel is not evidence that an actual panic/dump cycle has succeeded.

The collector runs every five seconds with a 128 MiB rotating log bound, a 64 MiB service memory limit, 5% of one CPU, sixteen tasks, no capabilities and no IP-network access. Journal retention is capped at 512 MiB with a 4 GiB reserve. The installer preserves configuration bytes/modes and prior runtime sysctls/service/radio state, restores changed settings on failed activation/verification, and refuses independent edits or altered backups during rollback. It verifies durable journal delivery and two fresh telemetry samples before applying the optional Wi-Fi mitigation. Original acceptance artifacts, dump files and backups are not deleted.

The dry-run diagnostic package plan contains only `nvme-cli` 2.16-1 and `rfkill` 2.41.3-3ubuntu2.2, with no upgrades/removals or additional dependencies. SMART health will be read after the privileged tool install. The host's installed `linux-generic` and `linux-firmware` match their cached APT candidates; no kernel or firmware change has been applied. [ASUS's model-specific support page](https://www.asus.com/uk/supportonly/nuc8i5beh/helpdesk_bios/) lists BIOS 0098, dated April 10, 2026, while the host has 0095. The vendor description only identifies a platform issue fix, not this reproduced freeze. The [vendor instructions](https://dlcdnets.asus.com/pub/ASUS/NUC/IG_UG/ASUS-NUC-Visual-BIOS-Update.pdf) were reviewed, but no BIOS package was verified, flashed or scheduled for activation.

Local validation passed 89 storage/supervision/host-diagnostic tests, including twenty focused diagnostic cases. Those cases cover disk-only output, fsync, byte/file retention bounds, torn-record preservation, exclusive writer protection, symlink/hard-link rejection, atomic live status, real-host observations, package-plan guards, exact file/mode rollback, injected activation verification failure with runtime-sysctl restoration, wired-route requirements and changed-radio refusal. The focused suite also passed on the NUC without privileges. The systemd unit passed `systemd-analyze verify` outside the local sandbox; an earlier sandbox invocation could not set systemd socket options and is not represented as a unit failure. No intentional panic, hardware watchdog reset, BIOS flash, live root installation or across-reboot verification has been performed at this preparation checkpoint. Sudo still requires the operator's interactive authentication, so a checksummed, reviewable bundle and launcher must be staged before requesting that single privileged action. Acceptance remains stopped.
