# NUC repeat freeze and BIOS update preparation

The operator reported another unresponsive NUC, restarted it and disabled Wi-Fi and Bluetooth in BIOS. Live SSH inspection on November 9 verified Intel NUC8i5BEH / NUC8BEB, still running BIOS `BECFL357.86A.0095.2023.0918.1953` and kernel `7.0.0-42-generic`. At 14:59:51 UTC, 15:59:51 Prague time, current boot `18665649-0174-4c75-99fa-74d4fcc333c9` had 7,022 seconds of uptime, fresh telemetry about 1.54 seconds old, about 6.89 GB available RAM, full unused swap and zero global OOM kills. Docker, Tailscale and the diagnostic logger were active with zero recorded service restarts in this boot. Both the Wi-Fi PHY inventory and Bluetooth adapter inventory were empty, and rfkill reported no devices, consistent with the operator's BIOS radio disable. The default route remained wired `eno1`. Two distinct, valid signed public discovery heartbeats independently confirmed the existing version 1.0.0/protocol 13 identity; this is discovery liveness, not rendered gameplay or private account validation.

The operator ran the staged read-only exporter with interactive sudo. Its sanitized report contains numeric telemetry and crash-file metadata only. The old long-running boot's last durable observation is **November 5 at 20:37:21 UTC, 21:37:21 Prague time**, at 97,901 seconds of host uptime. It shows 6,792,040,448 bytes available memory, untouched swap, zero global or container OOM kills, load 0.23/0.13/0.10 and a hottest valid sensor reading of 42 degrees Celsius. The final consecutive CPU sample window was about 96.26 percent idle. Across 18,644 retained observations from that boot, available memory never fell below 6,260,314,112 bytes and the global OOM counter stayed zero. These observations provide no evidence of memory exhaustion, CPU saturation or high temperature at the last saved instant; they do not establish the exact freeze instant or rule out a later unrecorded fault.

A complete bounded scan of that boot's 1,472 retained kernel records, 1,022,980 bytes, found no actual panic/oops/lockup, OOM, machine-check, NVMe timeout/reset, filesystem error or critical thermal signature. The initial broad pattern matched normal DRM panic-plane registration and an i915 VGA decode-change line; those are benign startup messages, not fatal events. The last retained system journal entry predates the final independent numeric telemetry. The two short November 9 boots before the current boot have normal shutdown tails, so they are kept separate from the old failed boot. No normal shutdown or suspend explaining the November 5 interruption was established. The cause remains unestablished.

The protected dump directory contains only `kdump_lock` and `kexec_cmd` control files; both live pstore and archived pstore are empty. No crash dump was captured. The current capture kernel remains armed with 512 MiB reserved, watchdog/NMI watchdog and hard/soft-lockup panic enabled, panic-on-oops enabled and panic timeout 30 seconds. These kernel controls do not prove hardware-watchdog recovery or guarantee capture during a total host/firmware lockup. No raw memory dump, key, password, game state or configuration contents were exported. The [sanitized receipt](2026-11-09-nuc-repeat-freeze.json) binds the original safe files and exporter hashes; private numeric originals remain in the local staging directory and the operator export remains on the NUC.

[ASUS's exact-model support page](https://www.asus.com/uk/supportonly/nuc8i5beh/helpdesk_bios/) currently lists BIOS 0098, dated April 10, 2026, for NUC8i3BEx/NUC8i5BEx/NUC8i7BEx. The official [full package](https://dlcdnets.asus.com/pub/ASUS/NUC/NUC_8_Kit/BECFL357.86A.0098.zip) was downloaded to local disk and matched ASUS SHA256 `ef36336839565952a1ce1734b6ba93e9ec275d81ab54cbe235b5b1f7842aec7a`; ZIP CRC verification passed. The included F7 image `BE0098.bio` is 10,874,912 bytes, SHA256 `a1df7dbfb693f7b9d5b618ef12f21d0e1c05a15f87783da68388fafdcf6b143a`. Its included release notes identify production BIOS `BECFL357.86A.0098.2026.0204.1428` and list improved legacy-boot support. The website's general platform-fix description is not evidence that this recurring freeze is fixed.

The release notes warn that EC firmware flashing requires LPCClockRun disabled and Legacy S3 sleep, otherwise boot failure can result. The NUC currently exposes EC firmware 3.26, already equal to the package's target 3.26, and Linux reports `s2idle [deep]`, consistent with S3 selected. LPCClockRun was not verified through Linux; no hidden register, NVRAM setting or separate EC updater was read or changed. This caveat must not be silently discarded or treated as a verified F7 updater safeguard. The [ASUS F7 instructions](https://dlcdnets.asus.com/pub/ASUS/NUC/IG_UG/ASUS-NUC-Visual-BIOS-Update.pdf) use the package's designated `.bio` file on USB, with steady power and recorded/restored custom BIOS settings. The operator's disabled radios must be rechecked after any update or defaults reset. No firmware utility was executed, no BIOS flashed, and no host reboot, production deployment or diagnostic setting change was performed by this investigation.
